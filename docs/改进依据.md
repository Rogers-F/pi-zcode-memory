## E1 中文感知的提取门槛

**问题**：上游 `memory/extraction.ts` 用 `text.split(/\s+/).filter(Boolean).length >= 3` 判断「有用户散文」。中文句子通常没有空格，一句「记住：部署前要跑冒烟测试」只算 1 个词，永远达不到 3，于是中文用户最常用的记忆指令不会触发提取。

**依据**：

- Unicode Standard Annex #29, *Unicode Text Segmentation*（词边界规则，中文按词典/词边界切分而非空格）：<https://www.unicode.org/reports/tr29/>
- ECMA-402 *ECMAScript Internationalization API*, `Intl.Segmenter`（`granularity: "word"` 的 `isWordLike` 标记）：<https://tc39.es/ecma402/#segmentation>

**做法**：消息里出现 CJK 字符时，用 `Intl.Segmenter('zh', { granularity: 'word' })` 统计 `isWordLike` 段数；否则完全沿用上游的空白计数。因此英文（以及所有不含 CJK 的文本）结果逐字一致。阈值仍是 3。

**验证**：`npm run eval` 断言中文触发数严格高于上游、英文触发结果完全一致；`memory.test.cjs` 覆盖「中文无空格 / 中文有空格 / 英文 / 阈值边界」。

## E2 召回候选混合排序

**问题**：上游召回清单按 `mtimeMs` 倒序取前 200 条交给选择器。记忆越多，越早写下但仍然相关的条目越容易被挤出候选，选择器再准也看不到它们。

**依据**：

- G. V. Cormack, C. L. A. Clarke, S. Büttcher, *Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods*, SIGIR 2009：<https://dl.acm.org/doi/10.1145/1571941.1572114>
- S. Robertson, H. Zaragoza, *The Probabilistic Relevance Framework: BM25 and Beyond*, Foundations and Trends in IR, 2009：<https://doi.org/10.1561/1500000019>

**做法**：先按 BM25（文件名 + description，`k1=1.2`、`b=0.75`）排一次，再按修改时间排一次，用 RRF（`k=60`）融合，取前 200 条交给选择器。只改变交给选择器的候选集合与顺序；选择器系统提示、清单行格式、上限 200/30 全部不变。上游的清单在会话内是「粘」的（建好后整段复用，选择器对话才能累积），所以 E2 只在建清单时按当时的问题排一次：会话内第一次召回、压缩之后、Dream 改动记忆之后。

**验证**：`npm run eval` 在离线数据集上断言 Recall@5 高于纯时间排序；`memory.test.cjs › E2 混合排序把相关旧记忆排进前 5` 断言相关旧记忆进入前 5，而时间排序的前 5 没有它。

## E3 提取时预载最相似的记忆

**问题**：提取 Agent 每轮只有 5 次模型请求，上游提示词要求「turn 1 把所有可能需要改的文件都读一遍」，但模型并不知道哪些文件与这次对话相似，经常直接新建文件，产生近似重复的记忆。

**依据**：

- Mem0, *Building Production-Ready AI Agents with Scalable Long-Term Memory*, arXiv:2504.19413：<https://arxiv.org/abs/2504.19413>（记忆更新/合并前先检索已有记忆）
- 上游 `memory/extraction.ts` 的既有策略：turn 1 并行读取、turn 2 并行写入——预载只是把「读哪些文件」从猜测变成检索结果。

**做法**：提取前用 BM25 + 时间 RRF（与 E2 同一个函数，但不依赖 E2 开关）按本次新消息里的用户文本选出最相似的 3 个记忆，把正文放进提取提示词末尾；完整读入的正文在 `ToolRunner.readPaths` 里标记为已读，这样 `Edit` 不需要再花一轮 `Read`（被截断的正文不算已读，仍要先 `Read`）。

**验证**：`npm run eval` 用确定性脚本模拟「有预载就更新、没有就新建」，断言重复文件数不高于关闭时且文件总数更少；`e2e.test.cjs › E3：提取时预载最相似的记忆正文；严格上游模式不预载` 断言提取请求里带上相似记忆正文、严格上游模式不带。

## E4 改写或删除前先归档

**问题**：上游 Dream 会直接改写或删除记忆文件，误合并、误删之后无法找回；宿主也没有回收站。

**依据**：

- FreeDesktop.org, *Trash Specification 1.0*：<https://specifications.freedesktop.org/trash/1.0/>（`$trash/files` 存原文件、`$trash/info/*.trashinfo` 存 `Path` 与 `DeletionDate`，允许扩展键）

**做法**：后台的 `Write`（覆盖已有文件）、`Edit`、`Bash rm` 在落盘前把旧内容复制到 `archive/<projectKey>/files/<相对路径>`，并在 `archive/<projectKey>/info/<相对路径>.trashinfo` 写入 `Path`（原绝对路径，百分号编码）、`DeletionDate` 与两个扩展键 `X-ZCodeMemory-Reason`（`overwrite` / `delete`）、`X-ZCodeMemory-Size`。文件名冲突时按回收站惯例加 `.1`、`.2` 后缀。面板的「归档」区可以恢复（原路径存在时拒绝覆盖）或彻底删除。

**验证**：`agent.test.cjs` 断言归档目录、trashinfo 字段、恢复与彻底删除；`e2e.test.cjs` 在 Dream 链路里断言两条归档（overwrite + delete）并能恢复；关闭 E4 时断言不产生归档。

## 严格上游模式

`strictUpstream = true` 时 `normalizeSettings` 强制把 E1–E4 置为 false：中文回到空白计数、候选回到时间排序、不做预载、改写不归档。`npm run eval` 的最后一组断言核对这一点，`core.test.cjs` 另有单元测试。
